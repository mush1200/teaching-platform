## 1. F1 更正確認：**我原本的說法過廣**

我在上一輪寫的是：

> 憑證是**買受人出具**的，代表退款流程要能**向 Buyer 索取證明單**。

**這句話在電子發票情境不成立。**

**統一發票使用辦法 §20-1 原文（已查證）：**

> 營業人銷售貨物或勞務開立電子發票後，若雙方合意退回或折讓，
> 應以網際網路或電子方式開立證明單，包含：
> **存根檔**（賣方自存，作記帳及申報扣減銷項稅額）、
> **收執檔**（交付買受人收執，**其為營業人者**，作為記帳憑證及申報扣減進項稅額之用）、
> **存證檔**（傳輸至平台存證）。

也就是說：**電子發票走「三檔電子流程」，不是紙本四聯單**，
而且條文本身就區分**買受人為營業人／非營業人**的不同用途。

**對方的修正正確。** 但我建議再精細一層 ——
**P14 的分流不只一個維度，而是三個：**

| 維度 | 分支 |
| --- | --- |
| 憑證型態 | 紙本統一發票（§20）／電子發票（§20-1）／小規模營業人免用統一發票之收據 |
| 買受人身分 | **營業人**（有統編，收執檔可作進項扣減）／**非營業人**（本平台主要客群：家長、教師個人） |
| 申報狀態 | 銷售額**已申報**／未申報 |

**本平台的買家以個人為主，多數無統一編號 → 屬非營業人**，
處理方式與 B2B 不同。`P14` 必須把這三個維度都留成分支，
不能只寫「依發票型態決定」。

## 2. `MR-18` 新語意：正確，但需要兩個防護

**對方的重定義：**

> `MR-18` PASS ＝ 所有 Deployment Gates 在 baseline 中**均存在、定義完整、
> 具有明確 acceptance criteria 與 implementation status**，
> 而不是「全部已經完成」。

**這是對的，而且是這輪最重要的結構決定。**
否則 20/20 在所有 code 寫完之前永遠不可能達成，
Full Baseline 這件事本身就失去意義。
`MR-16`／`MR-17` 套用同一語意（問「Gate 有沒有完整列出、狀態是否誠實」
而不是「律師簽字了嗎」）也正確 —— 文件本來就叫 `Pending Legal-Tax Validation`。

但這個放寬會製造兩個新風險，各需一個防護。

### 2.1 防護一：**三條狀態線必須分開顯示，永不合併**

一旦 `MR-18` 可以在零實作的情況下 PASS，
`FULL REGRESSION — PASSED (20/20)` 這句話就會被外部讀成「可以上線了」。

**建議 baseline 標頭固定三行，不得收斂成一行：**

```text
Document Regression:    PASSED (20/20)
Deployment Readiness:   x / 14 gates implemented
Legal / Tax Validation: PENDING
```

`Document Regression PASSED` **不蘊含**任何一項功能存在。

### 2.2 防護二：`implementation status` 必須有**證據指標**

「狀態是否誠實」是 `MR-16`～`MR-18` 新語意的核心要求，
但**誠實如果沒有驗證方式就沒有牙齒** ——
任何 Gate 都可以被標成 `IMPLEMENTED` 而沒有人查。

**建議：** 標為 `IMPLEMENTED` 的 Gate **必須附證據指標**
（檔案路徑、schema 欄位、測試名稱）。
標為 `NOT IMPLEMENTED` 則不需要。
這與 `G3` 第四款、`MR-20.11` 是同一套紀律。

**而且這件事現在就可以驗證，成本是一行指令：**

`db/db_schema.sql` **與 `Backend/`** 對
`payment_received_at` / `entitlement_status` / `terms_accepted` /
`consent_version` / `frozen` / `account_freeze`
**全部 0 命中**（schema 與後端程式碼皆無）。

| Gate | 目前狀態（schema ＋ backend） |

| Gate 1 Account Freeze | **NOT IMPLEMENTED** |
| Gate 5 Consent versioning | **NOT IMPLEMENTED** |
| Gate 6 `payment_received_at` | **NOT IMPLEMENTED** |

## 3. 新發現

### 3.1 `ENTITLEMENT-RETENTION-INVARIANT` **沒有終止條件，會讓檔案回收永久癱瘓**

對方定義的 cleanup 判定條件是四類都要視為「仍有依賴」：

- active
- temporarily suspended
- **revoked but legally / audit-restorable**
- historical fulfillment snapshot

**問題出在第三類與第四類：**

「legally / audit-restorable」**沒有寫終止時點**。
若任何曾經存在過的 entitlement 都永遠算依賴，
那 `docs/material-file-storage-and-delivery.md` §8.5 的回收指令
**將永遠不會回收任何檔案** ——
一個為了保護資料而加入的不變條件，會把既有機制完全停用。

**建議：** `ENTITLEMENT-RETENTION-INVARIANT` 必須帶一個 **retention floor**，
且該 floor 要能說明來源。候選來源都已在本輪查證過：

| 來源 | 期間 |
| --- | --- |
| 消保法 §19 III 解除權最長暴露 | **4 個月** |
| 數位經濟產業個資辦法 §16 終止處理紀錄 | **5 年** |
| 稅務憑證保存 | 依 `PRE-TAX` 結果 |
| `PRE-04` 履約版本 | 依 Buyer license 存續期間 |

**取所有適用期間的最大值**，並在 baseline 寫明推導過程。
沒有 floor 的不變條件不是保護，是癱瘓。

### 3.2 `PRE-03.8` 的區分需要一個**可操作的判準**

對方的精準化正確：

> 「從 Creator 既有錢包／既有已得款項直接扣回」是 reopen trigger；
> Creator 違約產生的獨立損害賠償／下一期計算調整**不應自動被視為同一件事**。

**但這個區分在實作時會被爭論**，因為兩者的帳務結果可能相同。
需要一個可以測試的判準。

**建議寫進 `PRE-03.8`：**

> 判斷依據是**該調整的計算基礎**：
> 若基礎是「**某筆 Buyer 交易的款項**」→ 觸發 reopen；
> 若基礎是「**Platform 因 Creator 違約所受損害**」→ 不觸發。
>
> **操作性測試：** 若 Creator fault adjustment 的金額
> **恆等於該筆退款金額**，則實質上就是 clawback，只是換了名字。
> 損害賠償的金額應獨立計算，且**可能大於或小於**退款金額。

沒有這一條，`PRE-03.8` 的區分會退化成「取名字的藝術」，
而 `PRE-03` 全篇的立場正是**實質認定優先於名義**。

### 3.3 `P10` 四欄拆分要對應到 `PRE-03.8` 的判準

對方提出的四欄 ✅ 很好：

```text
current_period_gross_basis
current_period_excluded_refunds
creator_fault_adjustments
platform_absorbed_post_settlement_refunds
```

**補一句：** `creator_fault_adjustments` 這一欄
**必須另存「損害計算依據」**，而不只是金額。
否則稽核時無法區分它與 clawback ——
而那正是 §3.2 的操作性測試要驗的東西。

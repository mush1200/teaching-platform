## 1. `W1` 收窄：v1.6 正確，我原本的措辭過寬

我第五輪寫的是：

> Phase 1 不做 Buyer 端儲值、點數、**預付**、禮券或任何預收未指定商品價金的機制。

限定語「**未指定商品**」在句尾有寫，但把「預付」放進並列清單本身就會誤導 ——
目前「特定訂單 → Buyer 匯款 → Admin 核帳」本來就是預付型態，
而那正是 Phase 1 要保留的流程。**v1.6 改名為 `BUYER-STORED-VALUE-LIMIT` 是正確的修正。**

## 2. 法源查證

### 2.1 電支條例 §3「多用途支付使用」—— v1.6 的援用成立

**原文：**

> **多用途支付使用**：指電子支付帳戶或儲值卡內之儲值款項，
> 得用於支付**電子支付機構以外之人**所提供之商品或服務對價、
> 政府部門各種款項及其他經主管機關核准之款項。

**排除：**

> 不包括**僅得向發行人所指定之人請求交付或提供商品或服務之商品（服務）禮券**
> （另排除各級政府機關發行之儲值卡等情形）。

**因此 v1.6 的兩層區分成立：**

| 情形 | 適用 |
| --- | --- |
| 只能買平台自己教材的禮券／點數 | **禮券規範**；因非「多用途」，**不當然落入電支** |
| 可跨商家、可支付第三方商品服務 | 禮券規範 **＋** 可能落入電支條例的「收受儲值款項」 |

> v1.6 說「不應寫成『任何禮券 = 電子支付』」—— **正確**。
> 分界線是「**是否可支付電子支付機構以外之人所提供之商品或服務**」。

### 2.2 禮券的排除條件 —— 分界線比 v1.6 寫的更明確

v1.6 把 Phase 1 允許項寫成
「Platform-issued discount code that **does not represent stored monetary value**」。

**條文的分界線不是「有沒有金額」，是「有沒有收錢」：**

> 商品（服務）禮券**不包括發行人無償發行之抵用券、折扣（價）券**，
> 及電子票證發行管理條例所稱之電子票證。

**關鍵字是「無償發行」。** 兩個實際後果：

| 設計 | 判定 |
| --- | --- |
| **免費**發放的 NT$100 抵用券 | **排除** —— 即使記載金額，因為是無償發行 |
| **付費購買**的「點數」，即使刻意設計成非金額型 | **不排除** —— 有償就可能是禮券 |

**修法：** `§15 Phase 1 Allowed` 的判準改為
「**無償發行**之抵用券／折扣（價）券」，
`Not Allowed` 的判準改為「**有償取得**、可用於未來未指定訂單的價值」。
用「有沒有 stored monetary value」當判準，會同時放過有償點數、誤擋免費抵用券。

### 2.3 一個附帶發現：禮券規範的主管機關**依附表分屬多部會**

該應記載事項的主管機關包含經濟部、農業部、衛福部、教育部、NCC、交通部、文化部、
財政部、退輔會等，**適用範圍依附表**。

也就是說，未來若真要發禮券，**「歸哪個部會管」取決於營業項目** ——
這直接強化 v1.5／v1.6 的 `P0 Operating Entity & Registered Business Scope`
是先決條件，而不是行政瑣事。

### 2.4 著作權法 §37 II

v1.6 `C1-A` 的援用正確：

> 前項授權不因著作財產權人嗣後將其著作財產權讓與或再為授權而受影響。

且 v1.6 正確指出它**不解決 head license 終止**的情形（`C6-A` 因此必要）。

## 3. 新發現

### `V1` —— `MASTER REGRESSION MATRIX` 自身有不對稱，會製造新的漂移

`MR-13` 把 **Buyer 端**的 stored-value 紅線提升為獨立一列 ✅。
但 **Creator 端的 Product Invariants 沒有任何 MR 編號**，只隱含在 `MR-01`（PRE-03）裡：

- No Creator Wallet
- No Creator Withdrawal
- No Creator Available Balance
- 不得使用「平台代你收款」「扣佣後餘額」等語言
- 退款以**淨銷售計算基礎**處理，**不得**做成從 Creator 餘額扣回
- Buyer UI 不把 Creator 稱為 Seller

**一邊顯性、一邊隱性，正是 Master Matrix 想消滅的那種不對稱。**
下一輪讀者掃過 MR 會看到 Buyer stored-value 被保護，卻不會看到 Creator payout 紅線。

**修法：** 新增
`MR-19 — Creator Payout & Seller-of-Record Invariants`
（涵蓋上列六項），與 `MR-13` 對稱。

---

### `V2` —— `PRE-03.8` 只擋 stored-value，擋不住更大的風險

`PRE-03.8 No Stored-Value Expansion` 規定：提出 wallet／prepaid／gift card／paid points／voucher
就必須 reopen `PRE-03`。**方向正確，但範圍太窄。**

第二輪確立的六個「會把定性拉回代收代付」的紅旗，**只有一個是 stored-value**：

| 紅旗 | 被 `PRE-03.8` 涵蓋？ |
| --- | --- |
| Creator 錢包餘額 | ⚠️ 部分（是 Creator 端，條文寫的是 Buyer 情境） |
| **Creator 自主提領** | ❌ |
| **退款從 Creator 未來分潤扣回** | ❌ |
| **Creator 完全決定售價、平台無定價權** | ❌ |
| **Buyer UI 顯示「賣家：Creator」** | ❌ |
| **條款寫「平台代 Creator 收款」** | ❌ |

再加上未來可能出現的：導入 split payment／marketplace payment、
讓 Creator 自行完成 KYC 並直接收款。

**「Creator 自主提領」對第三方支付定性的殺傷力，比一張禮券大得多**，
但目前不會觸發 reopen。

**修法：** `PRE-03.8` 改寫為 **`PRE-03.8 PRE-03 Reopen Triggers`**，
列出完整觸發清單（stored-value 只是其中一項），並明訂
「觸發任一項者，不得當作一般 feature 排進 Sprint，須先 reopen `PRE-03`」。

---

### `V3` —— `REGRESSION-PROTOCOL-01` 少一個狀態

v1.6 定義了兩種結果：`Full Regression Passed` 與 `Delta Review`。
但實際上還有第三種，而且正是目前的狀態：

> **完整文件存在，但回歸檢查發現缺列。**

沒有這個狀態，下一輪只能在「PASS」與「只是 delta」之間二選一，
而 v1.6 一旦輸出完整文件卻缺了某一列 MR，就沒有詞可以描述它。

**修法：** 協議加入三態 ——

| 狀態 | 條件 |
| --- | --- |
| `Delta Review` | 輸入是變更集，**不得**宣告回歸 |
| `Full Regression — FAILED (MR-xx missing)` | 完整文件，但有缺列 |
| `Full Regression — PASSED` | 完整文件且 `MR-01`～`MR-19` 全數在列 |
